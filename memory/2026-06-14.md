### Lessons (added)

1. **"Just trigger fresh rebuild" + a verify step = landmine.** I triggered the rebuild because the operator asked, but the verify step in `terraform-apply.yml` was a leftover from before the PR #733 split, and it surfaces a real bug (NEO4J_URI never set) in a way that *looks* like the rebuild failed. The rebuild didn't fail. The verify step did. Two different things. Next time: read the verify steps before claiming "the rebuild worked" — the verify steps are part of what gets called "the run succeeded."

2. **Comments lie.** The v2 comment at line 880 says "NEO4J_URI is set HERE in v2." It is not. The env_vars JSON at line 892-900 doesn't include it. The comment is from before a refactor and was never updated. When I'm tempted to trust a code comment over a code search, I should grep for the actual reference. 3. **"How is postgres handled?" was the right question.** The operator asked a load-bearing framing question that immediately revealed the right pattern. When I'm trying to fix one half of a split, the fastest way to figure out the contract is to look at the half that *isn't* split. The unimpeachable reference design is right there in the same file.

4. **Option 2 is the right answer when Option 1 is right but speculative.** The composite-in-`infra-actions` design is the right long-term answer. But shipping it without a second consumer is YAGNI. Landing the stopgap first gives us a real forcing function — once the chain works, the composite's API surface becomes obvious from the call site. Don't invent the abstraction in advance.

5. **The `needs:` chain is the right shape, not a callable workflow.** `workflow_call` would be cleaner architecturally (one source of truth for the writeback step) but adds a contract surface (callable workflows need `inputs`/`outputs`/`secrets` declarations) that the stopgap doesn't need. The chain via `needs:` is the smaller diff and doesn't add a new contract surface. If a second consumer appears, we revisit the callable-workflow question.
